§01Overview and architecture

Collect Edge is a proposed operator app and fleet service. It runs on rugged handhelds, wearables, iPads, Windows tablets and phones; pairs with Bluetooth gauges and torque tools; keeps working offline with an append-only sync queue; and is managed from the cloud (app versions, checklists, gauge pairings). It is the concept successor to DataMyte's legacy DATAMYTE 600 collector and builds on Revolution PRO (see §12).

What it does

  • Collects readings, answers, photos and signatures with or without network.
  • Pairs Bluetooth LE gauges and torque tools and checks gauge calibration status before use.
  • Syncs through an append-only queue with idempotent uploads and clear conflict rules.
  • Manages devices as a fleet: versions, checklists, pairings, remote wipe.
  • Feeds SPC Stream, Torque Insight and Gage Cloud with context-rich readings.

Architecture

Data flows left to right. Every write passes schema validation at ingest, lands in the tenant data plane with an immutable audit entry, and is exposed to apps, BI and agents through the same API. Anything an agent proposes comes back as a draft that a named person approves.

§03Getting started

Proposed The quickest path from an empty tenant to a first live result.

Five steps

  1. Enroll a device: scan the tenant QR code in the app, or push it through your MDM.
  2. Assign the device to a plant and line.
  3. Pair a Bluetooth gauge in Devices → Gauges (the gauge must have a current calibration in Gage Cloud).
  4. Publish a checklist to the device group.
  5. Collect a reading with Wi-Fi off, then turn it on and watch the queue drain.

First API call

Create a service client in Admin → Integrations, exchange its secret for a token, then call the API.

# 1. token (OAuth 2.0 client credentials)
curl -s -X POST https://auth.concept.example/oauth/token \
  -d grant_type=client_credentials -d client_id=$CLIENT_ID -d client_secret=$CLIENT_SECRET \
  -d scope="collect.read collect.write"
# 2. first call
curl -s https://acme.api.concept.example/v1/collect/devices?plant=plt_a -H "Authorization: Bearer $TOKEN"

§06REST API reference

Proposed REST over HTTPS, JSON bodies, base URL https://{tenant}.api.concept.example/v1. Every endpoint below is a design proposal; none is live.

Authentication

  • OAuth 2.0 client credentials for services; authorization code + PKCE for users; tokens are JWTs valid 15 minutes.
  • Scopes per product and verb: collect.read collect.write collect.admin. Plant-level claims restrict data to the plants granted.
  • Writes that change a released record (limits, plans, calibrations) require a user token and create a draft unless the user holds the approver role.

Draft and approval flow

  1. Agent calls a write tool; the server validates input and stores a draft with the evidence links.
  2. The owner gets a notification (Escalate, email or mobile push).
  3. A person with the approver role accepts, edits or rejects; acceptance applies the change and signs it (see §10).
  4. The agent receives the outcome by push notification or polling GET /drafts/{id}.

§08Statistics and methods

Collect Edge is offline-first: the device is the system of record until the server acknowledges a write. The rules below are Proposed design; the gauge values in the examples are Real dataset piston-ring diameters (Montgomery piston rings via the qcc R package).

Event log and identity

Every reading or checklist answer is an immutable event with a client-generated ULID, a device ID and a hybrid logical clock (HLC) timestamp:

HLCe=(max(twall,llast),c),c={clast+1if l=llast0otherwise

HLC keeps a causal order even when tablet clocks drift; the server stores both device time and receipt time.

Sync protocol

  1. Write locally first (SQLite/IndexedDB) and append to the outbound queue.
  2. When online, upload in queue order in batches of up to 500 events with an Idempotency-Key per batch.
  3. The server validates, de-duplicates by event ID and returns per-event acks.
  4. Acked events are marked synced; rejected events stay visible to the operator with the reason.
  5. Pull: the device fetches definitions (checklists, specs, gauge pairings) changed since its last sync_token.

Retry delay uses capped exponential backoff with full jitter:

dn=U(0,min(dmax,d0·2n)),d0=1 s,dmax=300 s

Conflict resolution

Data typeRuleWhy
Definitions (checklists, specs, pairings)Server wins; device re-pullsOne released version at a time
Results (readings, answers, photos)Append-only; never overwrittenAudit trail: originals are kept
CorrectionsNew event with corrects: <event_id> and a reasonShows both values and who changed it
Same result recorded twice (double sync)De-duplicate by event ULIDIdempotent upload
Result against a definition that changed while offlineAccept, flag definition_version mismatch for reviewNever lose floor data

An operator measures subgroup 25 of the piston-ring study while the tablet is offline. Spec 73.95–74.05 mm (as in the qcc vignette).

§09Integrations

Proposed Integration points. Vendor names are typical targets, none confirmed as partners.

OPC UA

The edge gateway runs an OPC UA client (Security Policy Basic256Sha256, Sign&Encrypt). Subscriptions map node IDs to characteristics; sampling interval and deadband are set per node.

# line signal used as context on readings
- node: "ns=3;s=Line3.Station2.PartPresent"
  context_field: part_present
  sampling_ms: 250

MQTT (Sparkplug B)

Gateways publish to the tenant broker over TLS 8883. Topic namespace spBv1.0/{group}/DDATA/{edge_node}/{device}; birth/death certificates mark devices online and offline.

spBv1.0/plantA/DDATA/gw-line3/tablet-12
{"timestamp":1760806931000,"metrics":[{"name":"queue_depth","datatype":"Int32","value":27}]}

MES / ERP

Serial and order context come from MES/ERP so each reading carries genealogy. Outbound webhooks push events; inbound REST accepts part, order and serial context so every result carries genealogy.

Power BI and BI tools

Device and event tables are available to BI for fleet and adoption reporting. A read-only OData v4 feed (/v1/odata/collect) exposes curated tables with row-level security inherited from the user's token; scheduled refresh uses a service principal.

Data protection

  • Per-tenant schema plus PostgreSQL row-level security; plant claims in every token.
  • Encryption: TLS 1.2+ in transit; AES-256 at rest; customer-managed keys (KMS) on enterprise plans.
  • Backups: point-in-time recovery 35 days; encrypted, region-pinned.
  • Retention: configurable per record type; legal hold blocks deletion.

§12Migration from the legacy product

The legacy product, as DataMyte describes it

Cited DataMyte lists the DATAMYTE 600 as a legacy product: its Microsoft operating system reached end of life on February 28, 2022 and it is no longer in production. Revolution PRO is the current rugged portable collector, with wired or Bluetooth gauging, Wi-Fi upload, offline data collection and a free Digital Clipboard license; the wrist version deploys on Android devices from several makers. Gauge pages name Mitutoyo, Sylvac and MicroRidge among compatible gauges. Sources: DATAMYTE 600 Data Collector, Revolution PRO, Wrist Revolution, Dimensional gauges (pages read Oct 17, 2026).

Migration path

Proposed

  1. Inventory remaining DATAMYTE 600 units and their routes.
  2. Convert inspection plans to Digital Clipboard checklists (CONVERT-ai can draft them).
  3. Run the new app on Revolution PRO or existing Android devices beside the old routes.
  4. Retire legacy collectors line by line.

FAQ

What happens if two devices record the same part?
Both results are kept. They are different events; duplicates are only removed when the event ID is identical.

Does it work with Revolution PRO?
Proposed: yes, as an Android app, alongside DataMyte's own software.

Is this DataMyte software?
